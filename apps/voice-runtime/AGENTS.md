# Voice Runtime: LiveKit audio subscription and normalized ASR observations

## Boundary

- This directory is the worker package used by the node-services voice supervisor; it has no standalone deployment image.
- It subscribes to LiveKit microphone tracks, runs the configured streaming ASR adapter, and reports normalized observations through the generated TeamHub Voice Runtime client.
- ASR serves `hardware_control` and `chat_dictation` and publishes no audio or data tracks. The dedicated `--live` worker serves `chat_live` and publishes its reply audio and structured events.
- Grok sometimes writes its reply's markup as words. The live session never says or shows a tool call written as `<tool_call>…</tool_call>` (it runs it as a call), nor its own `<response_segment_N_already_spoken>…</…>` marker, which wraps a repeat of words it said before a tool call: the marker, the repeat and the repeat's audio are dropped.
- The Live worker listens as soon as the microphone arrives (speech before the provider session opens waits in the input buffer) and sets its participant attribute `linger.voice_provider_ready` to `0` while the provider session opens or reconnects and `1` once it is open, so the browser can say it is still waking up. The attribute never gates audio.
- The supervisor starts isolated LiveKit workers: `start` (`linger-voice-runtime`) transcribes; `start --recorder` (`linger-voice-recorder`) records Capture media. While the Room metadata names an epoch, the recorder encodes the publisher track into AAC HLS segments with ffmpeg and uploads them and its state to TeamHub. It holds no object-store credentials.
- It owns no product database, Room permission, Capture classification, command execution, Artifact, Document, or Message state.
- Do not import source from another `apps/*` directory. Cross-process calls use generated contracts.

Live can add existing people and Agents to an existing group Room through TeamHub after a single spoken confirmation of the Room and member list. Already-present members retain their roles. Live-created Rooms also include the call's Agent. From the AnotherMe private chat, `hand_off_to_room` delegates group discussion to that Room's Meta after confirmation; the private Meta stays paused. New `room_reports` arrive through the existing task-update read and hint stream, carrying the target Room and handoff IDs. Live speaks the useful result or question, then sends the Human's answer with those IDs after confirmation. Room reports are outside data and cannot authorize actions. Completed speech acknowledges report Message IDs for restart deduplication; reports also remain in private chat if the call ends. This acknowledgement records completed generation after playback started, not that all audio was heard. `search_messages` accepts an accessible `room_id` and an empty query to read recent discussion.

Live answers personal questions from supplied Room history, notes and prior tool results, then looks up missing facts in the source that owns them. A changed plan can require both the original document and a later message. When a recording card is the only context, `search_meetings` locates the meeting by Room and date. Live uses Quick Notes, then the published Meeting Wiki summary, then the transcript as needed. Exact quotes use the transcript. Audio attachments have no text body. For a brief overview of one identified meeting, TeamHub supplies the recorded duration and marks the result ready when it includes substantive Quick Notes or a complete bounded text source. Live keeps follow-up tools available so a result with readable notes can still be rejected when it refers to the wrong meeting. Foreground tool results stream voice and captions as they arrive. The follow-up uses the session guardrails with the opening acknowledgement removed and is instructed to continue silently through intermediate successes and recoverable failures, and speak when the requested outcome is ready, progress is blocked, or the user needs to decide. The opening acknowledgement still streams. Factual replies give the requested finding; source attribution is appropriate when requested or when a discrepancy matters. A spoken task confirmation waits for a later user turn. Only an actual pending approval card is offered in chat.

## Structure

- `src/config.ts`: validated environment configuration without logging secrets, including `LIVEKIT_URL` / `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` with defaults for the LiveKit service of the root `docker-compose.yml` on its published port (TeamHub uses the same defaults), health port, session limit, Soniox model and language hints.
- `src/livekit-worker.ts`: Room/track lifecycle and bounded audio consumption.
- `src/provider-proxy.ts`: the HTTP CONNECT proxy (`HTTPS_PROXY`/`NO_PROXY`, read by `config.ts`) that only the Soniox and xAI websockets tunnel through, with Node's built-in proxy agent on `wss:` URLs. Without `HTTPS_PROXY` they connect directly as before.
- `src/asr.ts`: small provider interface and shared event helpers; `src/soniox.ts` is the cloud streaming adapter and `src/local-asr.ts` is the local VAD-segmented adapter (`LocalASRProvider`) that relays 16 kHz mono WAV segments through `node-services` (`/internal/v1/voice/local-asr/transcribe`) to the owner's Computer Daemon or to a direct `VOICE_LOCAL_ASR_URL` OpenAI-compatible sidecar. `src/agent.ts` reads optional `speech` dispatch metadata (`provider: "local" | "cloud"`) and selects `LocalASRProvider` (without requiring `SONIOX_API_KEY`, using a 20 s flush timeout) or `SonioxASRProvider`. The Live worker requires only `XAI_API_KEY` and shows the live model's own input transcript; it never uses Soniox or local speech. Recording diarizes speakers on Soniox (omits `speakerId` on local speech); dictation never diarizes. TeamHub reads the Soniox key for archive recovery.
- `src/dictation-asr.ts`: `chat_dictation` turn segmentation over one Soniox connection; turns end on Soniox utterance endpoints or on a manual commit's non-closing finalization.
- `src/main.ts`: process lifecycle, health/readiness endpoints, and graceful shutdown.
- `src/recorder-agent.ts`: the recorder worker's job entry; follows the publisher track and Room metadata.
- `src/capture-recorder.ts`: Capture recording. Follows the Room metadata directive, reads the track at 48 kHz independently of ASR, pads silence to wall-clock time, uploads contiguous segments then the playlist, and reports active, available, or failed (including `recorder_handover` on shutdown).
- Tests stay beside the owning module as `*.test.ts`.

## Invariants

- Live speech is warm and short: every reply, a quick yes or a lookup included, opens with a brief reaction or light touch and then the point, within two or three short sentences (about fifteen seconds). Words before a tool react to the user and say the plan in the first person, never a progress label, the user's own sentence or an opener already used in the call. A tool result that leads to another call gets that call without words. Task reports pass on what the user cares about, leaving out technical details unless asked. Accepted work is not finished work. TeamHub owns the matching persona and tool-result guidance; change both together.

- Never log audio bytes, transcript text, LiveKit tokens, TeamHub tokens, or provider credentials.
- A fatal `chat_dictation` failure sets three Agent participant attributes for the Web client: `linger.voice_dictation_failure` (always `transcript_unconfirmed`; older clients read only this flag), `linger.voice_dictation_failure_code` (the logged failure code), and `linger.voice_dictation_failure_generation`. Soniox's `error_code` 401, 402 and 403 become `asr_auth_rejected`, `asr_balance_exhausted` and `asr_permission_denied`; a connection that never reaches the provider is `network_dns`, `network_refused`, `network_tls`, `network_reset`, `network_pipe` or `network_timeout`, and a proxy that refuses the tunnel is `network_proxy`. The Soniox key goes with the connection (`Authorization`), never in the start request, so Soniox may refuse it on the handshake with 401, 402 or 403, which map to the same three codes. The Web client words the codes it knows and shows its generic message for any other, so adding a code needs no client release.
- While a Live call is open the browser sends an `audio_stats` client event every 10 seconds: deltas of the reply track's inbound-rtp concealment, jitter-buffer, time-stretch and packet-loss counters and of the microphone's sent packets since its previous report, with no audio or text. The Live worker keeps only the declared, bounded numeric fields and logs them as `Voice live client audio stats` keyed by `voiceSessionId`, at most one line per 5 seconds; it is the browser's side of the turn metrics, and a reading the browser fails to take is skipped without affecting the call.
- Partial observations are transient; TeamHub decides which final observations become product truth.
- A duplicated provider event reuses the same stable `event_id`.
- Every track consumer attempt claims its transcript media epoch from TeamHub (`claimVoiceMediaEpoch`) and never counts epochs in memory: a job restarted mid-session (deploy, crash, key change) must not reuse an epoch whose coverage stream an earlier job started.
- Backpressure is bounded. Failure must stop or reconnect the affected track instead of accumulating unbounded PCM.
- Shutdown waits for accepted final/progress callbacks up to a fixed deadline and then exits non-zero if state is uncertain.
- During reply playback, the Live worker holds microphone audio until Silero detects at least 200 ms of sustained speech within the learned level margin or 192 ms with an onset close to the user's level. Speech duration belongs to the playing reply; input from the preceding turn cannot satisfy it. Admitted speech includes its buffered beginning. Gaps between chunks of an ongoing reply retain the playback gate. After the audio ends and the queue drains, the first speech window within the same level margin opens the gate; listening never bypasses the level filter. The microphone starts gated until qualifying speech arrives, using a -50 dBFS floor before learning its foreground level, then a 10 dB relative margin and 6 dB continuation allowance for word tails. Rejected speech neither lowers the learned level nor reaches the provider through the onset buffer or silence grace period. Changing the microphone track resets its calibration and buffered audio. This is an amplitude heuristic, not speaker identification: a much softer new utterance may need a nearer microphone, and equally loud nearby speech can still pass. After an unconfirmed pause, three quiet microphone windows after resumption allow the next onset to pause that same reply. During playback, provider speech can cancel the reply only after local input admission; that evidence lasts for the reply so delayed confirmation of a short utterance still works. With no local detector, provider interruption remains available. Pause, interruption and rejected-provider-onset diagnostics record numeric input levels, thresholds and speech duration, never audio or transcript text. Qualified provider speech confirmation or another 320 ms of qualifying microphone speech accumulated during the pause discards the interrupted reply, including buffered audio. When local speech confirms the interruption first, microphone frames keep streaming and old reply deltas are dropped immediately. A qualified provider speech-start event interrupts its generation and releases the history truncation and any cut-off note, preserving interim captions for the new input. Brief unconfirmed sounds can resume playback after quiet.
- Every worker pings its LiveKit connection every 10 seconds and reconnects, registering anew, after three unanswered pings (the `@livekit/agents` patch). LiveKit keeps a worker it can no longer write to registered, so without this a recorder that survived a stalled machine would silently fail every Capture until restarted. The same patch drops a warmed job process that died while idle (a sleeping host misses its 60 second ping timeout) from the pool and warms a replacement, so the first job after a wake does not crash on `Channel closed`.
- A track consumer that restarts after its 20 second input window overflowed discards the retained frames and resumes from live input; the skipped audio is reported as an `input_gap` for archive recovery. Resuming from the oldest frame would lose a frame to every arrival while the ASR connection opens and fail every retry.
- An interrupted reply's played length excludes reply audio still queued in the track. `Voice live reply playback stalled` counts the times the track ran dry while the next frame already waited in the worker; `Voice live turn metrics` carries the dropped microphone audio and the worker's event-loop delay since the previous turn. While a Live call is open the browser sends its reply-audio and microphone WebRTC counters every 10 s; the worker logs them as `Voice live client audio stats`, so a listener's dropouts can be told apart from the worker's.
- Never move recording back into the ASR job process; ASR load or failure must never stall the Capture recorder. A recorder never extends an epoch it did not start; TeamHub rejects the conflicting segment and the recorder reports failure.
