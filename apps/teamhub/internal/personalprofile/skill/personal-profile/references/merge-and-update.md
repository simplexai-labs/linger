# Merge, conflict, and lifecycle rules

## Incremental updates without raw archives

This is the normal maintenance path after the initial profile. A daily update begins with newly available information, not a fresh reconstruction of the whole person. Initial extraction remains the primary workflow in SKILL.md; a quality complaint or explicit full rebuild is a separate task.

1. Read the current derived understanding, general source scope, and optional source_sync boundaries. Identify the authorized update interval and sources that can have new or changed material. A newly connected source may receive its own focused first pass without rebuilding existing sources.
2. Read eligible changes using the connector's supported change feed or time filters. Use the last successful source boundary, not the profile's modification time. Capture the next upper boundary at the start of the source pass. If no reliable boundary exists, use the requested period or a disclosed bounded recent window appropriate to the cadence; do not automatically restart historical extraction.
3. Open earlier related context only when a new item needs it: to resolve identity, connect a product and organization, interpret a change in status, or evaluate a consequential contradiction. Unrelated old threads and every previously sparse module are not part of the daily scope. A bounded overlap can account for retrieval granularity; deduplicate derived meaning without saving message IDs.
4. Classify the effect of the new material: no useful change, independent support for an existing pattern, complementary detail, a new fact or practice, a status change, or a genuine contradiction. Repeated notices about one event are not independent support. One event need not become a stable preference or habit.
5. Integrate supported changes into existing observations and connected passages. Reuse source and block IDs where appropriate, preserve names and responsibility boundaries, retain relevant history with its status, and keep unrelated detail intact. Update the summary only when its claims are affected. Do not append a daily message log or rewrite all modules to make the profile look fresh.
6. After successful review of an interval, advance only the completed source's source_sync boundary. Do not advance through an unread page, failed read, or unprocessed interval. Other successful sources may progress independently. See State and tools for the minimal derived-only metadata. No source content, item IDs, external cursors, or event ledger is retained.
7. Save and render any actual state changes, inspect affected passages, and give a brief accurate update when a response is needed. Distinguish information changes from synchronization progress. With no meaningful new understanding, keep prose unchanged; zero or one new observation is a valid daily result. Do not invoke the optional recomposition guard or widen historical reading simply because nothing changed.

Use the same claim-specific support, authority, and privacy rules as initial extraction. A new role can change current work without erasing useful history; a parallel engagement need not replace existing employment. If a change affects multiple passages, update those dependents together. A direct user correction overrides prior ordinary evidence within its scope.

Source-level scan boundaries are generated bookkeeping, not raw evidence and not proof of exhaustive historical review. Older profiles remain usable without them. Preserve historical access limitations, and do not promise exact-once ingestion or detection of changes unsupported by the connector. Source-only synchronization does not require inventing profile content.

## Preserve meaning when merging

First distinguish duplicate material and events, equivalent meaning, complementary detail, contextual differences, and real changes over time. Only then consider contradiction. More messages or more sources do not win a vote.

| Situation | Action |
| --- | --- |
| One event appears in replies, a forward, and an automated notification | Treat it as one event in transient analysis, not repeated behavior. Save only the derived understanding. |
| Two independent statements establish the same preference in the same context | Keep one complete narrative and its general source associations. |
| Incoming mail establishes product scope; the user's reply describes their responsibility | Combine the supported relationship or keep complementary observations. Preserve both meanings. |
| One person owns different aspects of several products | Keep product and responsibility distinctions; do not compress them to a generic industry label. |
| Short internal updates and detailed client explanations | Preserve the audience difference. |
| A role is explicitly shown to replace an older one | Update current status; retain concise relevant career history with its time context. |
| Another role or client engagement is active concurrently | Keep both in the current-work account, grouped by company or engagement. Do not manufacture a career transition. |
| An offer follows ongoing employment correspondence | Retain the offer's status; do not assume departure, acceptance, or a completed transition. |
| Contemporary, equally applicable preferences cannot be reconciled | Suspend the ordinary disputed conclusion and present derived alternatives for confirmation. |
| A task asks for brevity while the user generally wants full analysis | Follow the task without rewriting the broader preference. |
| Equivalent understanding appears in different languages | Merge meaning while retaining useful detail and authority; translation creates no new evidence. |

There is no maximum number of blocks. Merge to remove true repetition, never to hit a size target. Preserve stable local block IDs and useful unaffected content. The reading layout may combine several related blocks into one connected paragraph without merging away their distinct meanings or support. The developed overview makes the person's present understandable; the modules retain the full detailed account.

## Authority depends on the kind of claim

- Explicit current user corrections and confirmations control the accepted understanding within their scope. Apply them directly; do not ask the same question again.
- An explicit preference supports the preference. Repeated attributable behavior can support a contextual pattern but does not automatically override a confirmed preference.
- Clear correspondence, shared documents, and records can establish the subject's context, responsibilities, behavior, choices, and scoped preferences without being user-authored. Evaluate reliability, attribution, time, and status for each conclusion rather than making self-authorship a universal requirement. An explicitly requested coverage correction may revisit previously omitted material. Routine updates do not reopen unrelated history merely because earlier coverage was partial, and rewriting prose alone does not broaden source coverage.
- Different audiences, periods, or tasks often explain variation. Preserve those distinctions instead of inventing conflict.
- Recency is a clue, not automatic authority. A newly received old document is not a new event.
- Silence is not confirmation. Skipped questions remain pending.

If ordinary evidence differs from confirmed understanding, keep the confirmed block active within its scope and surface the proposed change. If ordinary equally applicable conclusions conflict, suspend the affected blocks and remove them from the summary. Preserve independent, undisputed portions where possible.

## Things to Confirm

Ask only about genuine unresolved contradictions that matter. Explain the competing understandings in the user's language and name their general sources. Do not quote or reconstruct emails, retain confirmation wording, or attach message-level evidence.

A fictional example: two possible preferences for internal weekly updates are detailed background and risks, or key changes followed by next steps. Ask which currently applies, or whether each applies in a different setting. The user can choose, explain contexts, rewrite, or skip.

After an answer:

1. Store the accepted derived understanding, associated with a generic source whose kind is user_confirmation. Do not store the original reply, its locator, or its timestamp as evidence.
2. Preserve the context the user supplied; do not turn a scoped answer into a universal rule.
3. Update affected blocks and the summary, then remove the resolved conflict. Keep distinct useful facts and genuine unresolved questions.
4. If skipped, leave the question pending without restoring an ordinary disputed inference.

## Targeted recomposition for an explicit complaint

Use this path only when the user explicitly requests correction of an inadequate section. Ordinary incremental updates and installation of updated Skill guidance do not activate it automatically. A user may reject abstraction, emphasis, tone coverage, continuity, or headings even when the facts remain unchanged. Preserve confirmed understanding and unaffected detail while repairing that stated scope.

1. Identify the affected module and the current acceptance criterion before deciding whether there is nothing to update. Read its actual rendered text, not just the stored block count or change notes.
2. Read the current module-specific guide and reassess observations for the missing dimension. For Communication Style, task descriptions are not expression choices or tone. For Working Style, professional beliefs, responsibilities, and product capabilities are not a complete account of the subject's actual operating practices. New detail about rhythm, decisions, handoffs, tool functions, or contextual differences is complementary understanding, not a duplicate merely because it concerns the same project or source.
3. If the support is sufficient, write the affected passage afresh, preserving grounded facts, scope, and stable identifiers. If it lacks the needed expression or process detail, make targeted reads of relevant authorized material using those specific gaps. Do not substitute unrelated background checks, invent a workflow from a job title, or copy a reference profile's conclusions. If access is unavailable, state the actual limit and keep the account appropriately bounded.
4. Replace the affected composed sections, update the summary where needed, and migrate any stale presentation labels. A render command only formats the supplied text; it does not perform this analysis or rewrite an old paragraph automatically.
5. Save a repaired module using the helper's `--recompose-module` guard, then read its rendered body against the specific complaint. An unchanged body is rejected even when a heading, timestamp, source scope, or underlying observation changed. A changed adjective or vague sentence can still fail semantic review; the guard does not establish quality. Record new-source reading separately from improved synthesis, and explain actual unresolved gaps rather than claiming they were filled.

Do not trigger an unnecessary private-source rerun for an instruction-only Skill revision. The workflow above governs subsequent profile execution and any profile repair actually included in the authorized task.

## Updating the subject name

Use an explicit preferred name first, otherwise the verified display name, then a reliably extracted name. Preserve subject_id across name corrections. Update display_name and all summary, block, section, conflict, source, and change text wherever the name is used. Rewrite second-person prose naturally without changing facts or removing detail. Do not confuse a collaborator, signature persona, or sample name with the profile subject.

## Changing the output language

Keep subject identity, the resolved display name, local IDs, source associations, support basis, confirmation authority, exclusions, and unresolved meanings. Preserve name spelling unless the user chooses a localized form, and keep narration in third person. Translate all generated display text, including topical section headings and content, module headings, summary, narratives, source summaries, conflicts, and coverage notes. Preserve proper names when appropriate. Replace the prior rendered language instead of creating inconsistent parallel profiles.

A language change is not new evidence. Do not re-read personal sources solely to translate already-derived understanding, infer a permanent language preference, or keep original source quotes as a translation aid. Check that details and uncertainty survive translation.

## Explain, correct, remove, and forget

**Explain:** describe the conclusion's support type and general source scope. Be transparent that exact messages are not retained. Do not fabricate a quotation or a source link. If the user explicitly wants renewed verification, re-read only authorized relevant material and continue to avoid retaining raw copies.

**Correct:** apply a clear replacement directly. If the user says a conclusion is wrong without a replacement, remove or suspend it first. Do not require proof of the correction.

**Remove a conclusion:** delete it and update the summary, composed sections, and pending questions. **Forget information:** also remove synonymous or translated versions and known task-created output/candidate copies. Source overviews and change notes must not preserve the forgotten content in disguise. Preserve other useful unaffected understanding.

**Stop reading a source** and **delete information derived from it** are different requests. Follow the actual request. Deleting source-derived information removes its associations and any conclusions no longer supported; keep independently supported understanding only when consistent with the user's request.

For an explicit source-wide exclusion, store only its generated local source ID in excluded_source_ids, remove the source record, its source_sync entry, and affected associations, and enforce the restriction in later reads. For an item-specific exclusion, honor it during the active task without saving raw item identifiers or forgotten details. Explain the limitation if persistent recognition is requested; do not claim to recognize every future reappearance without retained identifiers.

Do not delete the user's original emails/files or unrelated backups. The helper creates no historical backups. Clean known task-created derived candidates and outputs as appropriate. Tool/provider histories and other systems are outside this Skill's erasure control.
